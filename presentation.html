Visión General

Descripción del proyecto

PMT MLSecOps es un sistema de detección de ataques web basado en Machine Learning con un pipeline MLOps automatizado. Clasifica peticiones HTTP como normales o maliciosas (SQL Injection, XSS, Path Traversal, etc.) usando el dataset académico CSIC 2010 (~61.000 requests, ~41% ataques).

No es solo un modelo entrenado: implementa un ciclo de vida completo con gobernanza de modelos, roles de seguridad (Blue Team y Red Team) y feedback loop para re-entrenamiento. El objetivo es demostrar (a modo de ejercicio teórico/práctico) cómo operar ML en ciberseguridad con procesos, no solo con notebooks aislados.

Desarrollado por el Instituto de Seguridad de la Información (CSIC, España). Contiene miles de peticiones HTTP dirigidas a un e-commerce, como benchmark académico para detección de ataques web. Utilizamos un formato tabular (Kaggle).

Tipos de ataques cubiertos

Information Gathering, Files Disclosure, Cross-Site Scripting (XSS), SQL Injection (SQLi), CRLF Injection, Cross-Site Request Forgery (CSRF), Parameter Tampering.

¿Por qué un dataset balanceado (59:41)?

El ratio no representa un entorno de producción real (< 1% ataques). Sin embargo, brinda ventajas:

  • Training estable: Permite aprender clases minoritarias sin remuestreo sintético (SMOTE).
  • Baseline confiable: Métricas claras antes del rigor del desbalance operativo.

* Para compensar el desbalance de producción, se aplica Threshold Calibration.

Limitaciones y Mitigación

Antigüedad Faltan técnicas modernas (JSON, GraphQL, Desync). 🛡️ Red Team Agent prueba payloads frescos (GitHub).
Morfología Baja variedad de paths vs. red real. 🛡️ Feedback Loop (re-train si detección < 85%).

Stage 1: Exploración (EDA)

Análisis profundo en csic2010_eda.ipynb antes de escribir código de producción. Aquí no hay DAGs, solo investigación humana para descubrir dónde viven los patrones de ataque.

📊 Hallazgos en Métodos HTTP

Método Normales Ataques % Ataque
GET 28.000 15.088 35%
POST 8.000 9.580 54%
PUT 0 397 100%

* El método PUT es un indicador perfecto de compromiso.

📉 Calidad de Datos

Se encontró que ~70% de las filas no tienen body (peticiones GET). Se decidió fijar content_length = 0 en lugar de imputar con la media para evitar sesgos.

🛠️ Decisiones para Preprocessing

El EDA define las reglas empíricas que luego MLOps automatizará en el Stage 2:

  • Descarte de Ruido: Se eliminan 11 columnas irrelevantes o constantes (ej. User-Agent, Accept).
  • One-Hot Encoding: El método HTTP pasa a ser method_is_get, method_is_post, method_is_put.
  • Regex Features: Se crean variables binarias para indicadores de ataque como %27 (SQLi), script (XSS) y SELECT.

MLOps en Acción

Stage 4: Train Model A (Automatizado)

El DAG de Airflow orquesta el entrenamiento en producción, pero siguiendo un principio DRY (Don't Repeat Yourself): el script usa exactamente la misma función (train_model_a) que Data Science usó en el Stage 3.

📐 Criterios de Aceptación (Threshold Calibration)

En datasets desbalanceados de seguridad, el threshold de clasificación nunca es 0.5. Se busca el threshold óptimo que cumpla con los siguientes criterios duros:

  • Recall ≥ 0.95: Detectar al menos el 95% de los ataques reales.
  • Precision ≥ 0.75: De las alertas positivas, al menos el 75% deben ser ataques reales.
  • Gap val-test ≤ 0.05: Diferencia de precisión entre validación y test para evitar overfitting.
Si el modelo no pasa estos criterios, Falla y NO se registra.

⚙️ Detalle de Ejecución (train_model_a.py)

  1. Carga de datos: Lee features_v5.parquet del Stage 2.
  2. Split Estratificado: 70% Train, 15% Val, 15% Test (mantiene el ratio 59:41).
  3. Pipelines Nativos: Envuelve un StandardScaler (para variables continuas) y el clasificador dentro de un Pipeline de Scikit-Learn para un empaquetado 100% atómico y prolijo (adiós a exportar archivos scaler_info.json sueltos).
  4. Training & Auto-Selección: Entrena los 4 algoritmos (Regresión, RF, XGBoost, LightGBM) desde cero, los evalúa y elige automáticamente al ganador. ¡El algoritmo no está hardcodeado!
  5. Thresholding: Busca matemáticamente el punto óptimo en validación para alcanzar Recall ≥ 0.95 maximizando Precision.

Stage 5: Promote to Staging

El Gatekeeper Automático. Este proceso orquestado actúa como puente formal entre el entorno de Machine Learning (creación) y Ciberseguridad (evaluación).

⚙️ Pipeline de Promoción (dag_promote_model.py)

  • Ejecutor: Tarea 100% automatizada orquestada por Airflow.
  • Filtro de Seguridad (Regla de Negocio): Escanea todos los modelos experimentales y exige un mínimo innegociable: Recall >= 0.95 (no podemos dejar pasar ataques).
  • Selección del Campeón: Entre los modelos que aprueban, selecciona automáticamente el que tenga la mayor Precisión (para evitar bloquear tráfico sano).
  • Tags vs Aliases: Al ganador se le asigna el Tag candidate (metadata de estado) y simultáneamente el Alias staging (el puntero técnico de entorno). Finalmente, dispara la alerta al Blue Team vía AWS SNS/Slack.

Blue Team en Acción

Stage 6: Auditoría Blue Team

El Blue Team entra en escena. Las métricas matemáticas no bastan; un experto humano debe validar que el modelo es robusto frente a ataques reales y técnicas de evasión antes de tocar el tráfico de producción.

🛡️ Proceso de Auditoría Manual

  • Despliegue Aislado (FastAPI): Se levanta un microservicio que descarga el modelo de MLflow y expone endpoints de seguridad:
    • GET /health: Estado del servicio y modelo cargado.
    • GET /model/info: Auditoría de versión y threshold.
    • POST /predict y /predict/http: Predicción por features o HTTP crudo.
    • POST /model/approve: Sella criptográficamente la auditoría.
  • Ataques Ofensivos: Se lanzan baterías de pruebas manuales y automatizadas contra los endpoints (DAST, Fuzzing).
  • Prueba de Falsos Positivos: Se inyecta tráfico legítimo complejo para asegurar que no se bloquee a usuarios reales por error.
  • Decisión Final (Firma del SOC): Si sobrevive, el SOC dispara el endpoint /model/approve. Esto cambia el Tag a approved, pero deja el Alias intacto en staging. Es un pase formal para que el DAG de Producción (Stage 7) haga su magia.

MLOps / DevOps

Stage 7: Deploy a Producción

El despliegue a producción no es manual. Vuelve a tomar el control MLOps mediante un DAG de Airflow (dag_deploy_prod) diseñado bajo principios de Zero Trust.

⚙️ Automatización Segura

  • Validación Estricta (Zero Trust): El pipeline lee el Model Registry. Si la etiqueta no es exactamente approved, el despliegue falla inmediatamente. Nadie puede bypassear al Blue Team.
  • Promoción en Registry: Si está aprobado, Airflow le asigna el nuevo Alias production (dejando intacto staging por si hay fallbacks) y actualiza el Tag a production guardando el timestamp exacto del evento (deployed_at).
  • Notificación al Red Team: El ciclo de seguridad nunca termina. Al desplegar, se dispara una alerta automática avisando al Red Team que hay un nuevo objetivo en Producción listo para ser atacado (DAST continuo).

Operación

Stage 8: API Serving

El modelo llega a su destino final. Se integra al WAF (Web Application Firewall) para proteger la infraestructura crítica de la empresa en tiempo real, operado por el equipo de AppSec / SecOps.

🌐 Inferencia Dinámica

  • Pull de Producción: La API de inferencia (FastAPI) arranca y descarga automáticamente el binario del modelo que posea el alias production.
  • State-of-the-Art Pipelines: Como el entrenamiento (Stage 4) empacó el escalador y el modelo en un único Scikit-Learn Pipeline, la API no tiene que lidiar con archivos sueltos (ej. el antiguo scaler_info.json). Pasa los datos crudos y el Pipeline hace el escalado al vuelo internamente.
  • Latencia Ultra-baja: XGBoost fue elegido justamente por su velocidad. Bloquear o dejar pasar un request toma solo fracciones de milisegundo, sin afectar la experiencia del usuario.

Red Team en Acción

Stage 10.1: OSINT & Threat Intelligence

Agente 1: Payload Hunter (GAN Seed)

En una GAN clásica, el Generador arranca con ruido aleatorio. En nuestra Macro-GAN Semántica, el Agente 1 usa OSINT para crear el Espacio Latente (Latent Space) de inyecciones altamente realistas.

📥 Input (Fuente)

URLs crudas de repositorios de GitHub (ej. PayloadsAllTheThings).

⚙️ Pruebas (Técnica)

Parsing heurístico con LLM para separar ruido y extraer inyecciones puras.

🎯 Target (Objetivo)

Repositorios Open Source de Cyber Threat Intelligence (CTI).

📤 Output (Salida)

JSON estructurado listo para inyección.

Red Team en Acción

Stage 10.2: Adversarial ML (Simulación)

Macro-GAN Semántica (Arquitectura)

Reemplazamos las inestables GANs tradicionales por un Enfoque Generativo Basado en LLMs. El Agente 2 actúa como un Generador Adversario Inteligente.

🧠 Generador (Agent 2)

Propone payloads ofensivos (SQLi, XSS) basados en el OSINT extraído.

🛡️ Discriminador (XGBoost WAF)

La API de Producción (Stage 8) evalúa la petición. Devuelve 403 (Bloqueado) o 200 (Permitido).

🔄 Feedback Loop (Mutación)

Si el ataque es bloqueado, el Agente razona la falla y muta el payload (ofuscación, encoding) iterativamente hasta lograr el Bypass.

El Ciclo GAN (CrewAI Flow)

Utilizamos Process.sequential para inyectar el JSON de CTI en el Simulador. Luego, comienza la batalla iterativa Generador vs Discriminador.
